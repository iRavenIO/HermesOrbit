# Evidence and Assumptions Appendix

## 1. Purpose

This appendix separates what is already supported by evidence from what is still a strategic assumption.

That distinction is important because HermesMob is strong conceptually, but still pre-implementation and pre-traction.

## 2. What is already evidenced

### Product evidence
- Hermes already exists as a real agent platform with CLI, messaging, dashboard, and API-adjacent surfaces.
- A real iOS scaffold exists for HermesMob under `ios/` with generated Xcode project files.
- The documentation package includes a product blueprint, business plan, parity audit, API draft, roadmap, and research docs.

### Category evidence
- Public adjacent apps exist for mobile AI-agent operations, private/on-device AI, and developer agent supervision.
- App Store and web research found meaningful products in this space, including mobile command-center and self-hosted companion patterns.
- Public surveys and market reports indicate increasing investment in agentic AI.

### Workflow evidence
- The operational jobs HermesMob targets are real: alerts, approvals, job monitoring, remote intervention, and multi-instance status checks.
- Competing products prove that users will install mobile software for these jobs when the workflow value is clear.

## 3. What remains an assumption

### Commercial assumptions
- enough Hermes or adjacent users will pay for mobile operator control
- hosted conversion will be meaningful after self-hosted adoption
- pricing bands proposed in current docs match willingness to pay

### Product assumptions
- users want config, secrets, skills, and memory management from phone often enough to justify launch-tier investment
- native mobile UX will outperform mobile web enough to create retention and paid differentiation
- “operator console” framing will resonate more than “agent companion” framing in the market

### Execution assumptions
- a stable mobile API façade can be built without excessive coupling to Hermes internals
- App Review can be passed with the planned disclosures, demo path, and control model
- a small team can sequence product, backend, and push infrastructure efficiently

## 4. Sources used in the current package

### Public category and product sources referenced during research
- PwC AI agent survey
- Apple App Review Guidelines
- App Store public listings and iTunes Search API results
- Open Minis public site
- AgentsRoom App Store listing
- Onepilot public site
- self-hosted/open-source adjacent projects such as Marmy and CcCompanion

## 5. What this package does not yet prove

This package does **not yet** prove:
- live customer demand through interviews or paid pilots
- conversion rates
- staffing sufficiency
- time-to-ship estimate accuracy
- production-grade hosted architecture readiness
- legal clearance on naming or trademark use
- App Review approval certainty

## 6. What would upgrade confidence materially

### Evidence upgrades for product confidence
- user interviews with Hermes and adjacent operator users
- prioritized pain ranking by segment
- click-through or waitlist conversion on value propositions

### Evidence upgrades for commercial confidence
- paid beta or pre-order interest
- pricing sensitivity interviews
- proof that users prefer native mobile control over web fallback for key workflows

### Evidence upgrades for execution confidence
- deeper API façade contract
- implementation plan with team assumptions and duration ranges
- end-to-end prototype for connection, notification, and approval loop

## 7. Interpretation guidance

The right way to use this package today is:
- strong for investor conversations at thesis and opportunity level
- strong for internal alignment and implementation planning preparation
- not yet the same thing as a diligence-grade operating plan

## 8. Bottom line

The documentation package is strongest when presented honestly:

> **This is a well-researched, high-conviction product and business blueprint with real adjacent-market validation, but it is not yet a traction-proof company deck.**
